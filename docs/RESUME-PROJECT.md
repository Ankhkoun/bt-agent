## 一页简历版

**BT-Agent 长期个人 AI 助手｜项目设计与 AI 辅助开发｜时间待确认**

**项目概述：** 面向个人技术学习、实习准备与长期交流，设计基于 Pi 官方 Extension 的本地桌面 Agent。针对跨会话背景重复提供、学习反馈缺乏回答证据以及记忆容易混入 AI 推测的问题，通过五种交互模式、共享 Markdown Memory 和用户审阅机制，组织学习辅导、模拟面试、个人规划与日常对话。

**技术栈：** TypeScript、Node.js、Pi SDK / Extension、Next.js、React、Electron、Playwright Core、PDF.js。

**主要工作：**

- **设计多模式 Agent 上下文架构：** 通过 Extension 在每轮组合基础人格、当前模式与受限 Memory，使用原生 Session 自定义条目保存模式并按当前分支恢复，支持辅导、面试、规划与直接问答之间切换。
- **实现可审阅长期记忆流程：** 通过 `bt_memory_propose` 提交分类候选，核对当前分支原文并记录 Session/条目来源；由用户确认、拒绝或撤销，减少模型推测未经审阅进入长期上下文的风险。
- **设计带证据的学习反馈：** 约束 Tutor 先诊断、后教学与变式验证，将知识点、L0–L4 建议等级、回答依据、知识缺口及下一问题组织成 AI评估候选，避免把“熟悉术语”直接写为“已掌握”。
- **保护记忆历史与更新一致性：** 使用跨进程独占锁、revision 与 SHA-256 冲突检查、原子文件替换和事务意图恢复；撤销仅移除对应原样区块，保留其他记录与人工修改。
- **扩展真实资料工具链：** 基于原生 read 增加本地 PDF 文本提取、页码及分段读取，通过 Playwright 驱动专用 Edge 访问动态网页，使辅导和问答可基于实际资料开展。
- **完成桌面集成与场景回归：** 基于开源 Pi Web Desktop 定制 Electron/Next 界面，接通模式、Memory 审阅与模型配置；通过真实 Pi/Next、本地模型 fixture 和 Edge 测试验证核心链路。

**项目成果：** 交付可运行的 Windows 个人 Agent 桌面系统，完成“提出记忆候选—查看证据—用户确认—下轮加载—按条撤销”流程。2026-09-30 根测试 19 项、桌面测试 9 项、浏览器测试 2 项及隔离 UI 验证通过；未据此声称模型知识评估准确率或学习效果提升。

## 详细项目版

**BT-Agent 长期个人 AI 助手｜项目设计与 AI 辅助开发｜时间待确认**

**项目背景：** 在使用大模型学习技术、分析真实代码、准备面试和讨论个人目标时，同一用户的背景、知识缺口和既往决定容易分散在多个会话中。直接给答案不一定帮助判断是否掌握知识；把聊天摘要无差别写入记忆，也容易将用户观点、AI推测和未确认计划混为事实。项目以本人需求为设计输入，尝试将个人上下文、不同交互策略和可追溯反馈组织成一个可长期维护的桌面应用。此背景是设计动机，不代表已统计验证所有通用产品都存在相同缺陷。

**项目概述：** 基于官方 Pi Extension 构建长期个人 Agent，复用原生 AgentSession、工具循环与树状 Session，通过 General、Tutor、Interviewer、Planner、BT 五种模式分别支持直接问答、理解诊断、连续面试、目标取舍和开放交流。七份 Markdown Memory 维护个人背景、目标、任务、项目记录、知识地图、学习日志与共同主题。Agent 先提出有原文来源的候选，用户审阅后才追加到长期记忆；桌面端提供模式切换、Session 管理、Memory 审阅、模型配置以及本地资料入口。

**核心问题：** 如何在不同会话和交互目标下维持可控的个人上下文，并避免把模型推断和未经验证的学习评价固化为用户事实？

**技术栈：** TypeScript、Node.js、Pi SDK / Extension、Next.js、React、Electron、Playwright Core、PDF.js；Markdown 作为长期记录载体，JSON/JSONL 作为应用状态与原生 Session 载体。未引入 LangGraph、向量数据库、GraphRAG、MCP 或多 Agent 编排。

**主要工作：**

1. **设计分层上下文与模式状态：** 通过 `before_agent_start` 组合 SYSTEM、当前模式规则、Memory 和用户偏好；将模式变更记录为 `bt-mode-v1` 自定义条目，按 `getBranch()` 恢复，避免其他分支的模式污染当前会话。切换命令等待实际状态生效且不请求模型；Memory 每份和每轮均有字符预算。模式策略是提示词约束，测试验证注入与状态行为，没有证明真实模型始终遵循策略。
2. **构建可追溯记忆候选与用户审阅：** 设计 fact、user_view、ai_explanation、shared_question 类型；Agent 工具只提出候选，引用由程序在当前分支的用户/助手消息中匹配并捕获真实条目 ID。候选保存于私人审阅目录，确认前不进入 Markdown。提供桌面确认/拒绝/历史/撤销及无需模型的 CLI 审阅命令，把来源与写入决策暴露给用户。
3. **设计学习诊断与反馈记录：** Tutor 围绕实际知识点或代码片段要求用户解释，再定位缺口、针对性教学、重新解释和变化场景验证；Interviewer 完整轮次后才复盘。知识地图候选要求概念、建议等级、依据、缺口和下一验证问题，L3/L4 至少要求两条不同用户原文。评估持续标为 AI解释/待验证，不将引用存在或用户点击保存等同于真实掌握。
4. **实现记忆更新保护与恢复：** 共享 Node 存储协调 CLI 与桌面写入，使用独占锁和 revision 拒绝过时请求，比较候选生成时的目标文件 SHA-256，防止覆盖后来修改；通过 flush、临时文件替换和持久化事务意图恢复两文件更新。采用带唯一 ID 的追加区块，撤销只移除该条原样内容。保留原有私人 Markdown，冲突时停止覆盖并反馈；该方案不提供外部编辑器并发写入的数据库级保证。
5. **扩展文档与网页资料能力：** 通过官方工具扩展对 PDF 在本地提取文本并输出页码/分段结果，保留原生文本与图片行为；处理无文本层、损坏文件及体积/页数边界。Playwright Core 驱动专用 Edge，支持动态正文、点击、普通表单、标签页与截图；隔离日常浏览器资料，登录由用户在专用窗口完成。资料读取提供学习依据，未自动建设知识库或实现 OCR。
6. **集成桌面产品与端到端测试：** 基于 MIT Pi Web Desktop 定制 Electron → 回环 Next 服务 → Pi SDK 结构，复用成熟聊天、SSE、认证与原生会话能力；新增 BT 模式、个人 Memory 审阅等界面，接通 API 来源检查、Windows 代理与本地文件流程。以隔离 Memory、实际 Pi/Next、本地 SSE fixture 和真实 Edge 覆盖模式、工具执行、来源拒绝、审批持久化、撤销和窄屏使用。

**项目成果：** 已完成可运行桌面原型及候选审阅闭环，提供可以自行阅读与迁移的长期记录；本轮根类型检查、桌面类型检查/lint/生产构建、根 19 项测试、桌面 9 项测试、浏览器 2 项测试和 Memory UI 场景检查通过。构建保留 17 条动态文件 tracing 警告。用户反馈日常使用正常，但本轮未评测知识等级准确率、记忆语义正确率或学习效果，未验证独立安装包。2026-09-29 默认模型一次自动验收返回 403，不能被写成真实模型成功。

## 面试追问与回答要点

1. **为什么做 BT，现有聊天产品不能满足什么需求？** 以个人反复学习、面试、规划为动机；强调跨会话背景、不同交互节奏和反馈记录需要可控地组织。承认现有产品已有记忆能力，BT 的差异是可查看的分类记录、原文来源及用户审阅，不声称领先所有产品。
2. **你的个人贡献是什么，哪些代码由 AI 生成？** 明确本人提出需求与设计，AI 实现，本人与 AI 共同验收，无团队；举出自己确定的模式边界、记录类型和学习流程。对不熟悉的实现诚实说明，能现场解释的内容再作为简历技术点。
3. **为什么选择 Pi，如何避免只是换皮？** 复用工具循环、认证、Session 和 GUI 能减少基础工程重复；BT 新增层是模式状态、共享上下文、候选证据、人工审阅和学习记录。指向具体 Extension/存储/API/UI 和测试，避免把上游全部能力认领成从零开发。
4. **五种模式是多 Agent 吗，如何切换？** 同一 AgentSession 的行为规则切换；Extension 每轮注入当前规则，自定义 Session 条目持久化，按当前分支恢复；命令不调用模型。提示词约束不保证行为百分之百正确，需要单独模型评测。
5. **Session 与 Memory 有什么区别，为什么选 Markdown？** Session 是树状原始对话，Memory 是有选择的长期资料；共享 Memory 不随树回退。Markdown 便于审阅、备份和迁移，适合当前规模；短板是按文件前缀截断、无相关性检索和自动冲突合并，大规模时再评估检索方案。
6. **记忆引用真实，就能保证事实真实吗？** 不能。程序验证引用存在于当前分支，并保留消息角色和 ID；语义归类由模型提出、用户审阅。AI解释继续待验证，事实/观点要求用户原文。引用验证防止伪造来源，不等于事实核查。
7. **为什么需要 revision、哈希、锁和恢复意图？** revision 处理旧 UI，文件哈希发现候选生成后的外部修改，锁协调 BT 写入进程，原子替换避免半文件，意图恢复解决 Markdown 与状态分开持久化中断。解释异常锁人工恢复、外部编辑器未遵循锁及断电语义限制。
8. **如何撤销记忆而不删除后来的历史？** 每条已确认记录保存唯一 ID 与原样区块；撤销精确移除一个匹配区块。之后的其他记录保留；已人工编辑的区块无法安全匹配时返回冲突，不用整文件快照覆盖。
9. **Tutor 如何判断真正掌握，L0–L4 有验证吗？** 流程要求解释、应用或变式回答，结构记录依据、缺口和下一问题；等级是 AI建议，L3/L4 仅有最低证据条数约束。当前没有统计准确率或长期效果，后续应使用固定场景、人工标注和跨模型评测。
10. **怎样证明系统工作，失败路径有哪些？** 展示隔离 Pi 工具调用与生产 Next API、真实 Edge UI 测试；演示虚构证据拒绝、旧 revision 409、记忆变动冲突、事务恢复和撤销。模型 fixture 验证工程链路，不证明真实模型质量；403、扫描 PDF、网络与登录失败也要明确报告。

## 仍需确认

- 项目真实起止时间。
- 本人能够在不依赖 AI 提示的情况下解释或修改哪些模块；据此删减技术栈和工作条目。
- 是否实际试用本轮新增的候选审阅与知识评估记录；目前其证据来自隔离自动测试。
- 日常成功使用的实际 provider、模型、日期和典型场景；不需要提供密钥或私人对话正文。
- 是否已有真实学习复盘和面试场景的结果记录；没有时不能写“提高掌握率/面试通过率”。
- 是否正式采用上述角色表述；代码实现已确认由 AI 完成，不能改成独立手写或团队负责人。
